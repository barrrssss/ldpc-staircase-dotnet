# ldpc-staircase (.NET)

A general-purpose **systematic, fixed-rate LDPC-Staircase erasure code over GF(2)**,
following the RFC 5170 section 6 core constrained to the profile defined by the
shared specification.
Given `K` equal-length source symbols it produces `R` repair symbols by sparse XOR,
and a decoder reconstructs the source from `K + D` received symbols.

This is the C#/.NET implementation of the cross-language `ldpc-staircase` contract. The
normative specification and the conformance vectors live in the
[`ldpc-staircase-spec`](https://github.com/barrrssss/ldpc-staircase-spec) repository,
vendored here as the git submodule
[`external/ldpc-staircase-spec`](external/ldpc-staircase-spec). The vectors are
generated by `ldpc-staircase-java`; this library reproduces every one of them exactly
(see `ConformanceTests`), which is what makes the two runtimes interchangeable.

The library is deliberately **abstract** — symbol byte arrays in, symbol byte arrays
out. It performs no I/O, compression, encryption, framing, or page layout, and has
**no runtime dependencies**.

Current package version: **0.1.3**. It implements specification version **0.1.2**.
See [`CHANGELOG.md`](CHANGELOG.md) for implementation changes and the shared
specification's [`HISTORY.md`](external/ldpc-staircase-spec/HISTORY.md) for
cross-implementation decisions.

After the first NuGet release, install it with:

```sh
dotnet add package LdpcStaircase --version 0.1.3
```

## Not an MDS code

`erasure16` guarantees recovery from **any `K` of `K + R`** shards. This code does
not. It trades that exact guarantee for sparse XOR encoding and normally cheap,
low-memory recovery. The number of symbols actually needed is `K + D`, where `D`
depends on the graph, the seed, the decoder, and — heavily — the **shape** of the
loss. Always read completion from `DecodeResult.IsComplete`, never from a
received-symbol count.

Measured `D` is in `ldpc-staircase-java`'s `docs/measurements.md`. The short version at
`K = 2000`, `R = 1000`, `N1 = 7`: about 3 for scattered loss, and about 90 (p95 = 367)
when the lost symbols are one contiguous run of indices. That gap is the reason a
physical transport should interleave source and repair symbols across failure domains;
the transport layout remains outside this library.

## Profile (summary)

- RFC 5170 section 6 LDPC-Staircase core; systematic; one symbol per transport unit.
- Fixed `K` and `R`, decided before encoding; equal source/repair symbol length `S`.
- `N1 = 7` ones per source column by default; deterministic Park–Miller graph seed.
- Decode = degree-one peeling to a fixed point, then **at most one** complete residual
  GF(2) solve. No inactivation, no elimination-to-peeling cycles, no `G > 1`, no
  rateless stage.

See [`external/ldpc-staircase-spec/SPEC.md`](external/ldpc-staircase-spec/SPEC.md) for
the full normative contract, and `ldpc-staircase-java`'s `docs/decoder-design.md` for
how the decoder is built and what it costs — the two implementations share that design.

## Public API

```csharp
using LdpcStaircase;

var codec = LdpcStaircaseCodec.Create(sourceSymbolCount, repairSymbolCount, seed);
// or Create(..., seed, leftDegree) to override N1

codec.Encode(symbols);                       // fills repair slots [K..K+R) in place
DecodeResult result = codec.Decode(symbols, symbolPresent);
bool ok = codec.Verify(symbols);             // every parity equation XORs to zero

if (result.IsComplete)
{
    byte[] data = LdpcStaircaseCodec.Join(symbols, originalLength);
}

byte[][] symbols = LdpcStaircaseCodec.Split(data, sourceSymbolCount, symbolSize);
```

The type is `LdpcStaircaseCodec` rather than `LdpcStaircase` because the namespace
already holds that name; the Java class is `LdpcStaircase`. Everything else maps
one-to-one, in .NET casing.

`Decode` mutates both arrays: recovered symbols are written back and marked present.
Missing repair symbols fall out of the same equations and are recovered too. A received
set that does not determine the source is **not** an exception — it returns
`IsComplete == false` and lists what is still missing.

`DecodeOptions` bounds and instruments a decode:

```csharp
codec.Decode(symbols, present, DecodeOptions.Default
        .WithMaxResidualUnknowns(4096)               // refuse an oversized solve
        .WithProgressListener((done, total) => UpdateBar(done, total)));

codec.Decode(symbols, present, DecodeOptions.Default
        .WithResidualSolve(false));                  // peeling only (analysis, not production)
```

`ParityCheckMatrix` is public so loss simulation and layout work can inspect the graph.
`PmmsRandom` exposes the normative PRNG. Invalid parameters and malformed symbol arrays
throw `LdpcStaircaseException`.

## Cost

Release build, .NET 10, AMD Ryzen 7 5700U, `N1 = 7`, `R = K/2`, `S = 818` (a
representative medium symbol payload):

| K | R | build | encode | peel decode (R/2 lost) | residual decode (R lost) |
| --- | --- | --- | --- | --- | --- |
| 1,000 | 500 | 3 ms | 6 ms | 8 ms | 14 ms |
| 2,500 | 1,250 | 4 ms | 5 ms | 3 ms | 53 ms |
| 5,000 | 2,500 | 9 ms | 10 ms | 11 ms | 268 ms |
| 10,000 | 5,000 | 16 ms | 23 ms | 23 ms | 3,262 ms |

The last row is a stress case where a dense GF(2¹⁶) Reed–Solomon implementation was
estimated at about 401 MiB and roughly 1.9 hours. Generation and normal recovery are
milliseconds; the residual solve at the *full* repair budget is the only expensive
path, and it is quadratic, which is what `WithMaxResidualUnknowns` exists to bound.

Reproduce with:

```sh
LDPC_BENCH=true dotnet test -c Release --filter FullyQualifiedName~DecoderBenchmark
```

Run it in **Release**. In Debug the residual solve is about 4× slower, which is enough
to mislead. The equivalent Java run is roughly 1.6× faster on that column; the numbers
are directly comparable because both benchmarks use the same parameters, loss seeds,
and symbol length.

## Build and test

Requires the .NET 10 SDK (the library targets `netstandard2.0` and `net8.0`; the tests
target `net10.0`).

```sh
git submodule update --init   # pull the spec and conformance vectors
dotnet test LdpcStaircase.sln
```

`ConformanceTests` is the cross-language gate: it loads
`external/ldpc-staircase-spec/vectors/MANIFEST.json` and asserts byte-exact reproduction
of every PRNG, matrix, encode, and decode vector, plus the SHA-256 of each blob. It
fails loudly if the submodule is not checked out rather than passing vacuously.

The one place cross-runtime agreement could plausibly have broken is the PRNG's
`[0, maxv)` scaling, which SPEC.md section 3 pins to an IEEE 754 form that is *not*
equivalent to exact integer arithmetic. The `prngBounded` and `matrix` vectors are the
standing proof that .NET and the JVM agree: the largest matrix case alone consumes over
1,750 bounded draws, and a single divergent one would change the graph.

`ReferenceCorpusTests` is the independent-oracle gate of specification decision 0002.
Agreement between the two runtimes cannot rule out one shared misreading of `SPEC.md`,
because `ldpc-staircase-java` also generates the vectors both suites check against. The
spec repo therefore carries a dependency-free Python checker derived from the
specification rather than from either implementation, plus a differential corpus at
`external/ldpc-staircase-spec/reference/corpus.json`. This suite runs that corpus through
the .NET codec and compares every field with the checker's own answer.

It needs Python 3.11+ on `PATH` and runs the checker as an ordinary subprocess. Without
an interpreter the corpus check reports a skip so a developer build still runs; the
release gate turns that into a failure:

```sh
LDPC_REFERENCE_CORPUS_REQUIRED=1 dotnet test LdpcStaircase.sln
LDPC_PYTHON=/path/to/python3 dotnet test LdpcStaircase.sln
```

Create the NuGet and symbol packages locally with:

```sh
dotnet pack src/LdpcStaircase/LdpcStaircase.csproj -c Release
```

The package includes its README, license, notice, changelog, XML documentation,
repository metadata, and portable symbols. Publication is a deliberate manual step;
this repository does not define CI.

## Multi-targeting

The library targets `netstandard2.0` (the reach `erasure16-dotnet` has, including .NET
Framework) and `net8.0`. The only difference is `Symbols.XorInto`, the decoder's hot
loop: on `net8.0` it XORs 64-bit words through a safe `Span` view, and on
`netstandard2.0` it stays an unrolled byte loop because a wide view there would need a
`System.Memory` package reference or `unsafe` code. Both emit identical bytes — XOR is
byte-order agnostic — and the conformance vectors run against whichever the test project
resolves.
